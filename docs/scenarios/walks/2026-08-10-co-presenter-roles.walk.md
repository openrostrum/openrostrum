## Coverage anchors

- Canonical roles are `speaker`, `chairperson`, `moderator`, and `secondary` from `PARTICIPANT_ROLE`; a co-presenter is another `speaker` link. Exactly one ordered speaker is primary whenever speakers exist, and non-speakers cannot retain `is_primary=1`.
- Role-link uniqueness is `participants_submission_contact_role_uq(submission_id, contact_id, role)`. CFP reconciliation keys retained rows by `${contactId}:${role}`, preserving participant ID and `acceptance_status` while updating `position`/`is_primary` to the submitted ordering; replay returns `addedParticipants=[]` and cannot resend.
- Form policy is `forms.notify_existing_contacts` (non-null, default true). Notifications run only for confirmed inserts after commit; self/submitter delivery is suppressed; policy-suppressed existing contacts still receive account/access provisioning; provider failure preserves the role link.
- Access provisioning verifies the persisted event/submission/contact/role aggregate and accepts only credential-free HTTP(S) origins. Credentialed users receive `portalUrl(origin, eventSlug, portalPublicId)` with dedupe `participant-added:<participantId>:portal:<accountId>`; passwordless users receive `${origin}/set-password/${token}` with dedupe `participant-added:<participantId>:<token>` and reuse the deterministic earliest active null-organization token. Contact linking is compare-and-swap protected.
- Portal actions are `add-participant`, `set-participant-role`, and `remove-participant`; source-form enabled roles/min/max, close gate, exact contact-role collision checks, and mutation-coupled primary clear/promotion are server-enforced. Role changes preserve participant ID, `position`, and `acceptance_status`.
- Portal ownership can come from any caller link, but ordered selection exposes one non-secondary participation control; confirm/withdraw updates all of that caller’s non-secondary links and leaves `secondary` acceptance untouched.
- Organizer attachment/editing uses the exact contact-role key without portal form-limit restrictions, preserves acceptance/position on relabel, and deterministically promotes the next speaker. Manual `form_id=NULL` rows use only validated `notificationContext='admin-manual-submission'`. Accept provisioning remains `participants.role = 'speaker'` only.
- Participant-added mail is `kind='transactional'`, so general unsubscribe suppression does not block it; source-form existing-contact policy is separate. Agenda code is unchanged: `admin.agenda` still projects `contactId` and `role`, excludes only `secondary` from conflict `speakerIds`, and public program queries still exclude secondary contacts.
